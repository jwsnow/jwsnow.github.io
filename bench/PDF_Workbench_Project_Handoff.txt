MILESTONE 5.6.2 — EXPERIMENTAL STRONG THIN/MEDIUM PEN SMOOTHING

CURRENT BUILD: Milestone 5.6.2
Visible About version: 5.6.2
Service-worker/cache version: pdf-workbench-m5.6.2-v1
Library schema version: unchanged

WHY THIS REVISION EXISTS
------------------------
During side-by-side real handwriting use, the user reported that Goodnotes inking still looks noticeably smoother than PDF Workbench. The user explicitly requested a MAJOR thin/medium Pen tuning experiment with the expectation that the final settings may later be backed off. This revision is therefore intentionally more aggressive than the conservative 5.5.x smoothing work.

5.6.2 EXPERIMENT
----------------
- 1.5 pt Thin Pen curve factor / handle cap changes from 0.205 / 0.72 to 0.27 / 0.90.
- 1.5 pt completed-stroke anchor stabilization changes from 0.58 to 0.86.
- 3 pt Medium Pen curve factor / handle cap changes from 0.155 / 0.62 to 0.225 / 0.82.
- 3 pt completed-stroke anchor stabilization changes from 0.36 to 0.68.
- 5.5 pt Thick Pen remains EXACTLY at 0.135 / 0.58 with zero anchor stabilization. Use it as an in-app control when comparing the experiment.
- Because the thin/medium stabilization is much stronger, deliberate-turn protection now begins around a 35-degree change in direction instead of roughly 45 degrees and can taper to a slightly lower minimum contribution. The goal is to suppress shallow edge wobble while still allowing mathematical symbols and handwriting corners to stay recognizable.
- Raw sampled points remain authoritative and unchanged. Eraser, Select/Lasso, persistence, session-only Undo/Redo, hit testing, and object transforms still operate on the same raw geometry.
- Live Pen drawing uses the stronger width-aware spline settings. Completed screen rendering and PDF export additionally use the stronger anchor stabilization, so a stroke may settle slightly smoother when the Pencil lifts.
- This is explicitly NOT presumed final tuning. After real handwriting comparison, expect to keep, reduce, or partly revert the thin and medium changes independently.

UNCHANGED / REGRESSION-SENSITIVE
--------------------------------
- Milestone 5.6.1 dedicated reusable live-Pen layer and O(current-stroke) Pen-up commit remain intact. Do not reintroduce dense-page full-overlay repaint on each Pen release.
- Highlighter behavior is unchanged.
- Thick Pen is unchanged and serves as a control.
- 5.6.0 White/Black blank pages remain unchanged.
- 5.5.9 rebuilt-PDF link policy remains unchanged.
- External-library bundling remains POSTPONED while Pen behavior is being field-tested.

TEST REQUEST
------------
Compare 1.5 pt and 3 pt handwriting directly with Goodnotes using ordinary lecture/scratch-work writing, especially small letters, fractions, parentheses, long algebraic strokes, and tight corners. Pay attention to both (a) whether shallow wobble/rough edges are visibly improved and (b) whether the smoothing begins to distort intentional corners or makes the stroke feel as if it changes too much on Pencil-up. The 5.5 pt Pen provides an unchanged Workbench reference.

MILESTONE 5.6.1 — DENSE-PAGE PEN RELEASE OPTIMIZATION

CURRENT BUILD: Milestone 5.6.1
Visible About version: 5.6.1
Service-worker/cache version: pdf-workbench-m5.6.1-v1
Library schema version: unchanged

WHY THIS REVISION EXISTS
------------------------
A real scratch-work session in 5.5.8 exposed progressively sluggish/non-responsive Pen behavior on page 2 after ordinary mathematical handwriting/highlighting had accumulated. The exported page was not pathologically dense for the intended classroom use. Diagnostics showed healthy Apple Pencil pointer delivery (no characteristic dropped-contact/page-stage failure signatures) but increasing synchronous Pen-up cost. The root cause was the opaque Pen finalization path: live Pen geometry was drawn directly onto the persistent annotation canvas, so every Pencil-up had to clear provisional tail geometry by repainting every annotation on the page.

5.6.1 FIX
---------
- Pen now has a dedicated reusable `live-pen-canvas`, parallel in principle to the already-optimized live Highlighter layer.
- During contact, all immediate/raw and finalized smoothed Pen progress is drawn only onto this temporary live layer. The persistent annotation canvas remains frozen with previously completed annotations.
- On Pencil-up/cancel, Workbench draws only the just-finished Pen stroke's exact completed/stabilized geometry onto the persistent annotation canvas, then clears the live Pen canvas for reuse.
- Pen release therefore changes from roughly O(all existing page annotations) to O(the just-finished stroke). A page with hundreds of prior strokes should not become progressively more expensive merely because another short stroke is completed.
- Same-page split instances receive the live Pen stroke and one-stroke commit independently, preserving the established shared-document/independent-view behavior.
- If an unrelated asynchronous exact annotation repaint occurs during an active Pen or Highlighter gesture, that active stroke is excluded from the persistent repaint so it cannot be accidentally committed twice.
- Existing Highlighter live-layer behavior is retained. Eraser deferred exact redraw, selection optimization, Pen smoothing/stabilization, raw editable points, export geometry, and annotation ordering are otherwise unchanged.

DIAGNOSTICS ADDED
-----------------
`handler-begin-accepted` and `handler-finish-accepted` now identify the live layer and include the current page annotation count and history depth. Pen completion additionally reports `liveCommitMs`, `penCommitMs`, and `penCommitStages`. These are intended to verify during classroom use that Pen release remains nearly independent of page density.

PRE-RELEASE VALIDATION
----------------------
- Browser smoke testing created a black generated page, drew Pen ink, verified the reusable live Pen canvas is empty after release, and confirmed annotation Undo -> Redo restores the exact same annotation-canvas pixels. Highlighter still removes its temporary live layer normally.
- A synthetic dense-page comparison used 220 opaque Pen strokes with about 30 sampled points per stroke. On the same headless Chromium run, 5.6.0 average synchronous pointer-up processing rose from about 0.87 ms early to 2.62 ms late; 5.6.1 measured about 0.30 ms early and 0.29 ms late. This is not an iPad performance guarantee, but it confirms that the old page-density growth is removed from the Pen-release drawing path.
- An identical 30-stroke synthetic drawing produced byte-for-byte identical PNG data from the completed persistent annotation canvas in 5.6.0 and 5.6.1. Completed Pen appearance therefore remains unchanged by the live-layer architecture in this test.

FIELD-TEST / DISTRIBUTION DECISION
----------------------------------
- External-library/CDN bundling was considered for the classroom test but is POSTPONED at the user's request until this newly discovered Pen performance defect is addressed and field-tested. Do not treat 5.6.1 as the bundled/self-contained build.
- Continue using the existing pinned external library versions/caching behavior from 5.6.0 for this revision.
- The user plans a multi-day real-world classroom test after the Pen fix is validated.

UNCHANGED
---------
- 5.6.0 White/Black blank-page creation/insertion.
- 5.5.9 rebuilt-PDF link policy: preserve external URI links, strip internal/document-navigation links.
- 50-step session-only Undo stack; no memory cap has been added preemptively.
- Apple Pencil/Surface/Chromebook input architecture, partial Eraser, Select/Lasso, Highlighter, images, persistence/export, 0.94 touch-scroll inertia, Presentation ratio, graph paper, and end-of-document behavior.

CURRENT ROADMAP NOTE
--------------------
The roadmap list below remains authoritative. Its first item (performance/stability checkpoint) is now actively being exercised by this 5.6.1 Pen fix. After real-world validation, return to the remaining possibilities rather than treating external-library bundling as feature work. Bundling remains a deployment hardening task to revisit before/after the classroom field test as appropriate.

MILESTONE 5.0.2 — PDF INK EXPORT JOIN/CAP FIX
====================================================================

User-reported export defect after initial 5.0.1 pen testing:
- Wider curved strokes showed repeated white wedges/slits on the inside of turns in the exported PDF. The effect was especially visible in the thick black and green sample curves.
- This was distinct from the planned later interpolation/smoothing work. The stored stroke was a sampled polyline, but the immediate white-gap defect came from how that polyline was emitted to PDF.

Root cause and fix:
- 5.0.0/5.0.1 exported every adjacent sampled point pair as a separate `drawLine` operation, then added circles only at the two overall stroke ends. Separate PDF line segments do not form a joined stroke at their interior endpoints, so wider turns could expose triangular white gaps.
- 5.0.2 maps the same stored points to PDF coordinates but emits the complete stroke as ONE `drawSvgPath` polyline. The path is stroked with round line joins and round end caps.
- The enclosing PDF graphics state sets a round line join; `drawSvgPath` supplies the round cap and the existing stroke opacity. This preserves a single transparency operation for the stroke and avoids dark overlap nodes, which is useful groundwork for a future translucent Highlighter.
- Single-point taps still export as filled circles.
- No smoothing/interpolation is added here. Raw stored points and on-screen completed-stroke rendering remain unchanged.

Ink data architecture:
- Workbench ink is non-destructive page-local vector stroke data stored with each page. Each stroke contains an id, tool/type, color, width, opacity, and page-local point list.
- Stored coordinates are in the Workbench page's unrotated base-canvas coordinate system (PDF points, top-left origin), not screen pixels. Rendering maps those coordinates through current Workbench page rotation and zoom. Export maps them back through the source PDF's inherited page rotation/crop box.
- Same-document split panes share document content but preserve independent view state. Live strokes are mirrored into another rendered instance of the same page.
- Page state cloning was made annotation-aware so history, persistence, templates, duplication, page copy, Combine, backup restore, and backup-as-subtree do not accidentally alias mutable stroke arrays.
- Duplicate + notes carries Workbench ink. Duplicate clean omits Workbench ink.
- Page-size fit/center applies a proportional fit/center transform to existing Workbench ink. Margin/crop changes shift ink with the page content; resetting edge adjustments shifts it back. Page rotation needs no data mutation because rendering/export applies rotation to the page-local coordinates.

Export:
- Any page containing Workbench ink prevents untouched-byte passthrough for that document. An unannotated untouched source PDF remains byte-for-byte passthrough.
- Structural export adds Workbench strokes as vector PDF line/circle drawing operations; pages are not rasterized just to export ink.
- Source PDFs still use one batched copyPages call per source, preserving shared resources.
- Generated pages and image pages also receive Workbench ink before final page rotation is applied.

- `Back up editable Library` creates a ZIP-based `.pwbbackup` file.
- Backup contains all Library document records INCLUDING Trash state, folder hierarchy, persistent templates, original PDF/image source bytes, page edits/geometry/generated pages, undo/redo page snapshots, and saved open/single/split view session state.
- Current small local preferences (scroll mode, fit mode, Library Grid/List choice) are included.
- Backup file contains `manifest.json` plus binary source payloads under `sources/`.

Editable restore:
- Restore validates the backup format/schema before touching the current Library.
- Future/unsupported backup/schema versions are refused rather than guessed.
- Every document/template source reference is checked against the manifest.
- Every binary payload is read successfully before replacement begins.
- User receives an explicit warning that restore REPLACES the current Local Library and should back up first if needed.
- After validation, documents/sources/folders/meta are replaced in one IndexedDB transaction, then supported preferences are restored and PDF Workbench reloads into the backup's saved session.
- Pagehide persistence is suppressed during the restore reload so the pre-restore in-memory session cannot overwrite the restored session.

7. LARGE SCANNED PDF / JBIG2 BUG — IMPORTANT FIX
====================================================================

A large scanned PDF called:

    BaakeScan.pdf

was used as a test case.

Initially many pages appeared completely blank:
- in thumbnails
- in the main viewer
- on Windows
- on iPad
- rerendering/scrolling away and back did not fix them

The same pages displayed normally in Adobe Acrobat and Chrome’s built-in viewer.

Inspection of the actual PDF showed:
- 58 PDF pages
- 20 pages used ordinary JPEG images
- 38 pages used JBIG2 compression

The blank-page pattern corresponded to JBIG2 scan pages.

Root cause:
The custom PDF.js integration had configured the PDF.js worker but had NOT configured its WebAssembly decoder/resource paths.

Recent PDF.js versions use a WASM-based JBIG2 decoder, so the custom integration needed the correct resource configuration.

Fix implemented:
Provide PDF.js with:
- wasmUrl
- packed CMaps / cMapUrl as appropriate
- standardFontDataUrl
- WebAssembly support / decoder resources

After this change, the previously blank pages appeared normally.

IMPORTANT:
Do not remove or regress this configuration.
JBIG2 is common in scanned PDFs, so this is a required permanent compatibility feature.

Large scanned PDFs should also continue to use bounded canvas/rendering memory:
- do not eagerly retain every page object/canvas at high resolution
- render near the viewport
- release far-away canvases
- keep thumbnails lower resolution
- avoid excessive simultaneous raster renders

11. PINCH ZOOM — CURRENT UNRESOLVED BUG
====================================================================

This is the main known viewer bug after Milestone 2.1.0.

Observed on:
- Surface
- Chromebook
- iPad

Behavior:
When pinch-zooming, the visible scroll/document position jumps.

Desired behavior:
The PDF point under the midpoint of the user’s fingers before zoom should remain under the midpoint after zoom.

Correct algorithm concept:

1. Determine the pinch midpoint in viewer coordinates.
2. Determine the exact PDF/document coordinate under that midpoint BEFORE scaling.
3. Apply new scale.
4. Wait until the page/layout dimensions reflect the new zoom.
5. Measure actual post-layout geometry.
6. Adjust scrollLeft/scrollTop so the same PDF/document coordinate returns to the same screen midpoint.

Important:
The previous 2.1.0 approach tried to anchor pinch zoom but Surface still jumps.
Do NOT keep merely tuning the same ratio-only math.
The next revision should use actual before/after layout measurement.

Each pane must perform this independently.
The same document shown in both panes must not have one pane’s pinch zoom affect the other.

15. INKING REQUIREMENTS
====================================================================

Ink should NOT be raw straight line segments between pointer samples.

Use smooth local cubic interpolation, likely:
- Catmull–Rom → cubic Bézier
or a similar local spline method.

Do NOT use a highly global spline that creates oscillations.

For mathematical handwriting:
- smoothing must be conservative
- preserve sharp deliberate corners
- do not “correct” symbols excessively

Potential pipeline:

raw pointer samples
    ↓
remove near-duplicates
    ↓
light positional filtering
    ↓
local cubic interpolation
    ↓
pressure smoothing
    ↓
render variable-width stroke

Store original/sample data so strokes remain editable.

Stylus data may include:
- x
- y
- pressure
- timestamp
- potentially tilt/angle

Use coalesced pointer events where available for higher-frequency input.
Use predicted samples where available for lower visual latency.

Predicted ink is temporary only and must be replaced by real samples.

29. UI/UX PRINCIPLES TO PRESERVE
====================================================================

- Document gets the screen.
- Controls should be easy to find but take little permanent space.
- Presentation mode should be especially clean for classroom display.
- No hover-only functionality.
- Touch targets should stay comfortably tappable.
- Do not shrink buttons progressively into unusability.
- Prefer contextual controls.
- Pen/eraser/select state should survive navigation.
- Switching files should be fast.
- Split view should be a major feature, not an afterthought.
- Same document in both panes at different locations is explicitly desired.
- Full Page and Single layout icons must be visually distinguishable.
- Fit Page and Fit Width must be visually distinguishable.
- Avoid accidental destructive editing in Presentation mode.
