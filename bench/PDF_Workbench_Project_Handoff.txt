ARCHITECTURAL RULE
------------------
THE DOCUMENT IS SHARED; THE VIEW IS NOT. A structural document edit may change page indices, but an independent viewer instance should remain anchored to the same logical page/content whenever that page still exists.

- IntersectionObserver in split mode now controls only render/release of canvases, not current-page identity.
- Programmatic pane rebuild/restoration synchronizes the visible page after layout settles.
- Existing pending-page-focus protection remains in place during insertion, so a rebuilt pane cannot choose a different page before the inserted page is focused.

- The previous Milestone 2 split-view requirement remains: left/right are independent VIEW INSTANCES, including when the same PDF is displayed in both panes.

CURRENT BUILD: Milestone 3.4.2

Service-worker/cache version: pdf-workbench-m3.4.2-v1

THIS SECTION IS AUTHORITATIVE OVER OLDER STATUS TEXT BELOW.

RECENT 3.4.1 TEST FINDINGS
--------------------------
The 3.4.1 insertion patch exposed/confirmed a set of ordinary single-View synchronization problems:
- switching between ordinary open documents could apply the previous document's scroll location to the newly selected document;
- double-clicking a thumbnail in Pages could enter View at the top instead of at the selected page;
- in Page Snap mode, Save current page as template could capture a neighboring page (apparently often the next page);
- the first View insertion could land correctly but subsequent insertions could use the wrong side of the visibly current page.

Important diagnostic result: the same template save/insert operations work correctly when initiated from Pages. Therefore the document page model and template/page-copy machinery are considered sound; the fault is in single-View current-page/scroll synchronization.

Do NOT conflate the ordinary document-switch issue with the older Milestone 2 split-view work. The earlier split work concerned preserving independent left/right pane state, including same-document and different-document panes. The ordinary single-view switch behavior reported here is a newly discovered/current regression.

ROOT CAUSES / 3.4.2 FIX
------------------------
1. The single viewer previously let IntersectionObserver callback timing decide which page became current. In Page Snap/Continuous View, observer callback entry batches can promote a neighboring page even when another page is visibly centered.
2. When switching documents, loadDocumentState saved the outgoing document correctly, loaded the incoming document state, and then called renderAll() while the OLD document was still in the viewer DOM. renderAll() immediately saved that stale DOM scroll position into the newly selected document.
3. Pages double-click set activePageId but left a numeric saved scroll offset in the view. The subsequent render could restore that offset (often the top) instead of centering the requested page.

3.4.2 changes:
- in ordinary Continuous/Page Snap View, the page nearest the actual viewport center is authoritative;
- single-view scrolling schedules a lightweight viewport-center page synchronization;
- opening Insert in ordinary View explicitly synchronizes the visible page before capturing the page/template target;
- saving ordinary single-view state synchronizes the visible page before persisting page identity;
- document switching renders the incoming document with renderAll({saveState:false}), preventing the outgoing DOM from overwriting the incoming document's saved state;
- pending single-view page-sync animation frames are cancelled during document changes/rebuilds;
- Pages double-click clears stale single-view scroll restoration, focus-locks the chosen page, rebuilds View, and explicitly centers/renders that page;
- the 3.4.1 exact insertion-target and post-insert focus protection remains in place;
- no intended changes to split-pane state architecture, template session lifetime, narrow-toolbar behavior, touch/pen input, Presentation, output operations, or JBIG2/WASM configuration.

====================================================================
1. OVERALL PRODUCT GOAL
====================================================================

Build a local-processing PDF workbench with three broad working modes:

1. Organize / Pages
2. View / Annotate
3. Export

The app itself may be hosted, but PDF processing should happen locally in the browser. User PDFs do not need to be uploaded to a server.

Important philosophy:

- Touch-first, but excellent on Windows desktop too.
- Support mouse, trackpad, finger, stylus, Apple Pencil.
- Minimal permanent interface chrome.
- Full-screen / presentation-style viewing is central.
- Navigation and annotation tool state must be independent.
- The user should be able to scroll, zoom, change pages, switch files, or switch panes while Pen/Eraser/Select remains active.
- Document data and view-instance state must be separated.
- The same PDF may be displayed in two independent panes at different pages and zoom levels.
- Editing should be non-destructive until export.
- Recent local projects/files are desirable.
- The final app should be useful both for classroom presentation/annotation and general PDF assembly/cleanup.


====================================================================
2. ORIGINALLY REQUESTED PDF CAPABILITIES
====================================================================

The user initially asked for a general PDF tool that can:

- Combine images into a PDF.
- Combine PDFs.
- Mix PDFs and images in one output.
- Fix page size.
- Fix page orientation.
- Rotate pages.
- Compress PDFs to a maximum target file size.
- Rearrange pages.
- Delete pages.
- Duplicate pages.
- Extract selected pages.
- Split a PDF into groups of n pages.
- Potentially split by specified page ranges or one page per output.
- Normalize pages to Letter, Legal, A4, first-page size, or custom dimensions.
- Fit/center/crop content.
- Add margins / expand page canvas.
- Batch-process documents.
- Eventually support scan cleanup such as:
  - auto-crop
  - deskew
  - grayscale
  - black-and-white
  - blank-page detection
  - contrast/background cleanup
- Eventually support page numbering / simple headers/footers.
- ZIP multiple output PDFs where helpful.

OCR, editing existing PDF text, redaction, forms, digital signatures, bookmarks, etc. are NOT current priorities.

====================================================================

The app is being built as a PWA because the user wants one application that works on Windows, iPad, Surface, and Chromebook.

7. LARGE SCANNED PDF / JBIG2 BUG — IMPORTANT FIX
====================================================================

A large scanned PDF called:

    BaakeScan.pdf

was used as a test case.

Initially many pages appeared completely blank:
- in thumbnails
- in the main viewer
- on Windows
- on iPad
- rerendering/scrolling away and back did not fix them

The same pages displayed normally in Adobe Acrobat and Chrome’s built-in viewer.

Inspection of the actual PDF showed:
- 58 PDF pages
- 20 pages used ordinary JPEG images
- 38 pages used JBIG2 compression

The blank-page pattern corresponded to JBIG2 scan pages.

Root cause:
The custom PDF.js integration had configured the PDF.js worker but had NOT configured its WebAssembly decoder/resource paths.

Recent PDF.js versions use a WASM-based JBIG2 decoder, so the custom integration needed the correct resource configuration.

Fix implemented:
Provide PDF.js with:
- wasmUrl
- packed CMaps / cMapUrl as appropriate
- standardFontDataUrl
- WebAssembly support / decoder resources

After this change, the previously blank pages appeared normally.

IMPORTANT:
Do not remove or regress this configuration.
JBIG2 is common in scanned PDFs, so this is a required permanent compatibility feature.

Large scanned PDFs should also continue to use bounded canvas/rendering memory:
- do not eagerly retain every page object/canvas at high resolution
- render near the viewport
- release far-away canvases
- keep thumbnails lower resolution
- avoid excessive simultaneous raster renders

9. PRESENTATION MODE
====================================================================

Presentation mode is central to classroom use.

Goal:
The document gets the screen; controls appear only when needed.

Windows/desktop:
- True browser fullscreen is acceptable.

iPad:
- Do NOT invoke native Safari fullscreen.
- Native iPad fullscreen uses a downward swipe system gesture that conflicts with vertical PDF scrolling.
- Instead use app-level “chrome hidden” Presentation mode inside the PWA/browser content area.
- This has been tested and works much better, especially when installed from Home Screen.

Presentation toolbar behavior:

- Hidden by default.
- Appears when user moves/taps near the top.
- Auto-hides after a short delay.
- After using a toolbar button, auto-hide timer should restart.
- Hidden controls must NOT receive accidental clicks/taps.
- A tap whose purpose is merely to reveal the hidden toolbar must be consumed and must not also activate a button beneath it.

This tap-through bug previously existed.
As of Milestone 2.1.0:
- Surface testing indicates the hidden-control tap-through fix seems to work in ordinary cases.
- However, one earlier Chromebook/Presentation test found that when scrolled all the way to the top, touching the top could still hit a hidden-menu button.
- Milestone 2.1.0 was intended to fix this. Continue testing on iPad/Chromebook.

Presentation toolbar sizing:

Current requirement:
Do NOT progressively squeeze/shrink labeled buttons.

Use essentially a two-state toolbar:
- Wide enough: icon + text label
- Not wide enough: icon only

Keep practical touch/click target size.
Do not shrink buttons/text/padding through awkward intermediate sizes.

If still too narrow:
- remove labels
- tighten gaps moderately
- move secondary controls into overflow
- only use horizontal scrolling as a last resort

Surface testing of Milestone 2.1.0 found narrow-window button resizing still not acceptable.
The user specifically requested the simpler:
    labeled buttons → icons only
transition.

10. MULTI-DOCUMENT / SPLIT VIEW
====================================================================

Milestone 2.0.0 added split view.

Features already present:

- Two documents side by side.
- Each pane has its own document selector.
- Tap/click pane to make it active.
- Active pane indicated visually.
- Main viewer controls act on active pane.
- Each pane can have independent:
  - document
  - zoom
  - fit mode
  - current page
  - scroll position
  - viewing mode
- Full Page navigation can be controlled independently.
- Touch scrolling and pinch zoom intended to work independently.
- Split view works in Presentation mode.
- In split Presentation mode, L/R controls select which pane toolbar actions affect.

Important desired capability:
The SAME PDF may be open in both panes at different pages/zooms.
This is intentionally useful for teaching and is something Goodnotes cannot easily do without iPad multitasking.

Single/Split behavior required:

Single → Split:
- The current Single document should transfer into the active split pane at the same page/zoom/scroll state.
- The other split pane should restore its previous state if available.
- If no previous other-pane document exists, it may choose a sensible most-recently-used other document.

Split → Single:
- Whichever pane is active should become the Single view.
- Preserve its exact visible state.
- Preserve the inactive pane state in memory.

Single → Split again:
- The pane that had become Single should receive the updated Single state.
- The other pane should reappear exactly where it was left.

Example:

Start split:
LEFT = PDF A page 12 at 80%
RIGHT = PDF A page 47 at 120%

Make LEFT active → switch to Single.
In Single move to page 18, zoom 90%.
Switch back to Split.

Expected:
LEFT = PDF A page 18 at 90%
RIGHT = PDF A page 47 at 120%

Current status:
Milestone 2.1.0 improved Single↔Split transfer considerably on Surface.
Surface test said:
- selecting active pane from split and transferring seems to work better

However, before 2.1.0 there was a specific aliasing bug:
- If right pane was active
- choose a document
- switch to Single
- switch back to Split
- both panes could become the original right-pane document

2.1.0 was specifically intended to fix this by making left/right/single separate view instances rather than aliased state.

Continue testing this on:
- iPad
- Chromebook
- Surface

11. PINCH ZOOM — CURRENT UNRESOLVED BUG
====================================================================

This is the main known viewer bug after Milestone 2.1.0.

Observed on:
- Surface
- Chromebook
- iPad

Behavior:
When pinch-zooming, the visible scroll/document position jumps.

Desired behavior:
The PDF point under the midpoint of the user’s fingers before zoom should remain under the midpoint after zoom.

Correct algorithm concept:

1. Determine the pinch midpoint in viewer coordinates.
2. Determine the exact PDF/document coordinate under that midpoint BEFORE scaling.
3. Apply new scale.
4. Wait until the page/layout dimensions reflect the new zoom.
5. Measure actual post-layout geometry.
6. Adjust scrollLeft/scrollTop so the same PDF/document coordinate returns to the same screen midpoint.

Important:
The previous 2.1.0 approach tried to anchor pinch zoom but Surface still jumps.
Do NOT keep merely tuning the same ratio-only math.
The next revision should use actual before/after layout measurement.

Each pane must perform this independently.
The same document shown in both panes must not have one pane’s pinch zoom affect the other.

15. INKING REQUIREMENTS
====================================================================

Ink should NOT be raw straight line segments between pointer samples.

Use smooth local cubic interpolation, likely:
- Catmull–Rom → cubic Bézier
or a similar local spline method.

Do NOT use a highly global spline that creates oscillations.

For mathematical handwriting:
- smoothing must be conservative
- preserve sharp deliberate corners
- do not “correct” symbols excessively

Potential pipeline:

raw pointer samples
    ↓
remove near-duplicates
    ↓
light positional filtering
    ↓
local cubic interpolation
    ↓
pressure smoothing
    ↓
render variable-width stroke

Store original/sample data so strokes remain editable.

Stylus data may include:
- x
- y
- pressure
- timestamp
- potentially tilt/angle

Use coalesced pointer events where available for higher-frequency input.
Use predicted samples where available for lower visual latency.

Predicted ink is temporary only and must be replaced by real samples.

21. EXPORT / PDF MANIPULATION ENGINE — NEXT MAJOR FUNCTIONAL AREA
====================================================================

After Milestone 2 viewer state is stable, the planned next major phase is the actual output/manipulation engine.

Priority order:

1. Export current rearranged/rotated/duplicated page order.
2. Explicit merge/combine.
3. Extract selected pages.
4. Split every n pages.
5. Split by selected ranges/page numbers.
6. Image-to-PDF.
7. Normalize page size/orientation.
8. Crop/fit/center/margins.
9. Compression to target maximum size.
10. Batch operations / ZIP outputs.

Compression design:

First preserve structure where possible.

Progressive strategy:
1. Least destructive pass.
2. Recompress raster images.
3. Adjust image resolution/JPEG quality.
4. Iterate toward target file size.
5. If a strict maximum cannot otherwise be met, offer explicit rasterization fallback.

Important:
Do NOT silently rasterize selectable text just to hit a target.
If rasterization is required to guarantee file size, make it an explicit option.
